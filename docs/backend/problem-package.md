# Пакет задачи

Задачи добавляются pull request'ом в репозиторий задач
[lottery7/GpuCodeforcesProblems](https://github.com/lottery7/GpuCodeforcesProblems); через интерфейс их
не создают. Каждая задача — отдельный каталог в `problems/`. Имя каталога — постоянный ID задачи
(`[A-Za-z0-9._-]`), он виден в URL и хранится в посылках. Пакеты в том же формате лежат и в
[judge/problems/examples](../../judge/problems/examples): это данные тестов судьи и backend, не банк задач.

```
vector_add/
  statement.md    условие на русском с YAML-шапкой
  statement.en.md условие на английском, в шапке только название
  problem.json   ProblemSpec судьи без генератора
  problem.py     генератор тестов и эталон
  starter.cu     шаблон решения на CUDA (необязательно)
  starter.rtl.sv шаблоны других процессоров: starter.<процессор><расширение языка> (необязательно)
  format.json    формат и условия сравнения (необязательно)
  first.cu       первый код для guess, расширение — по языку задачи (first.sv, first.c, …)
  second.cu      второй код для guess
```

## statement.md и statement.en.md

Условие пишется на двух языках, оба файла обязательны: пакет без одного из них не импортируется.

`statement.md` — условие на русском и все метаданные задачи:

```markdown
---
code: "1"                 # номер в банке, по нему банк сортируется: числа по значению ("2" раньше "10")
title: Сложение векторов
difficulty: easy          # easy | medium | hard
tags: [CUDA, Векторы]
authors: [alice, bob]     # ники пользователей платформы
draft: false              # черновик видят и решают только авторы
---

Условие в Markdown: сигнатура, пример, ограничения.
```

`statement.en.md` — то же условие на английском. В его шапке только `title`; любое другое поле — ошибка пакета,
чтобы метаданные не разошлись между файлами:

```markdown
---
title: Vector Addition
---

The statement in Markdown: the signature, an example, the constraints.
```

Сайт показывает название и условие на языке интерфейса: frontend передаёт его в заголовке `Accept-Language`,
backend выбирает текст (без заголовка — русский). Поиск находит задачу по названию на любом из двух языков.
Теги общие для обоих языков. Версии задач, импортированные до двух языков, хранят один текст и показывают его
на обоих языках, пока пакет не обновится.

## problem.json и problem.py

Это ровно формат судьи, см. [judge/docs/problem-format.md](../../judge/docs/problem-format.md):
`problem.json` — `ProblemSpec` без поля `generator`, `problem.py` — модуль с `tests()`,
`generate()` и `reference()`. Поле `id` в `problem.json` нужно только `judge_cli.py`; backend
подставляет имя каталога. Пакет проверяется тем же `SpecValidator`, что и в gateway, поэтому
задача, которую не примет судья, не попадёт в банк.

## Процессоры и шаблоны

Процессоры задачи и языки на них задаёт `processors` в `problem.json` (см. формат судьи); без него задача
сдаётся только на `gpu-cuda` в CUDA. Процессор задачи, который платформа не предлагает (`PROCESSORS`), на сайте
не показывается.

Шаблон решения — свой на каждый процессор и язык: файл `starter.<процессор><расширение>`, например
`starter.gpu-cuda.cu`, `starter.rtl.sv`, `starter.riscv-rvv.c`, `starter.riscv-rvv.S`. Прежний `starter.cu`
служит шаблоном CUDA для `gpu-cuda` и `cuda-sim`. Без файла шаблон строится из сигнатуры: функция CUDA с ядром,
модуль `solve` с портами для `rtl`, функция C для `c`/`cpp`, заготовка для `asm`. Файл шаблона, который
не относится ни к одному процессору и языку задачи, — ошибка пакета.

Эталонных решений в пакете нет. Лимит каждого процессора автор подбирает сам: прогоняет своё решение через судью
(`judge_cli.py submit … --processor rtl --watch` печатает score) и ставит `limit` с запасом.

Блок «Окружение» на странице задачи — свой у каждого процессора: процессор и его модель (`platform.processors.models`,
для `gpu-cuda` — `GPU_NAME`), тип score, лимит, правила замера, для `rtl` — режим данных и порты. В нём же список
тестов процессора с пометкой замерных: backend не запускает генератор, поэтому список берётся из первой принятой
посылки на этом процессоре для текущего `judge_hash` (до неё блок говорит, что список появится позже).

## Форматы

Без `format.json` задача обычная. Формат `optimization` требует на каждом процессоре задачи рабочего шаблона
для его первого языка: `starter.<процессор><расширение>`, для CUDA также `starter.cu`. Шаблон, построенный
из сигнатуры, исходным решением не считается. Формат `guess` сравнивает два кода на одном процессоре и одном
языке: в `problem.json` должен быть ровно один процессор с одним языком (без `processors` это `gpu-cuda`
и CUDA), варианты лежат в `first<расширение>` и `second<расширение>` (`first.cu`, `first.sv`, `first.c`, …),
в `format.json` нужны непустые `explanation` и `explanationEn`.
Исходные коды проходят автоматическую проверку и замер через судью. Результаты не задаются автором:
поля `baselineTimeMs`, `firstTimeMs` и `secondTimeMs` запрещены в файле, включая значение `null`.
Старые снимки в базе продолжают читаться, но их числовые поля не заменяют новый замер.
Схемы и правила проверки описаны в [formats.md](formats.md).

Тексты `format.json`, которые видит участник, тоже двуязычны: поле без суффикса — русский текст, поле с суффиксом
`En` — английский. Если в файле есть `benchmark`, обязательны `inputDescription` и `inputDescriptionEn`; у угадывания
обязательны `explanation` и `explanationEn`.

Пример `format.json` для оптимизации:

```json
{
  "format":"optimization",
  "benchmark":{
    "inputDescription":"Векторы float32: N = 4, 1, 1000003, 25000000, 100000000",
    "inputDescriptionEn":"Vectors of float32: N = 4, 1, 1000003, 25000000, 100000000",
    "aggregation":"geometric_mean"
  }
}
```

Для угадывания задайте `format: "guess"` и добавьте `explanation` и `explanationEn`. Варианты кода хранятся
в отдельных файлах. Платформа измеряет оба варианта в одинаковом окружении процессора на тестах задачи;
после успешной проверки использует результаты для определения правильного ответа.
Результаты и объяснение не попадают в публичную деталь задачи до ответа пользователя.

В `benchmark` задаются описание входов `inputDescription` и агрегация `max` или `geometric_mean`.
Они применяются к score исходного решения, обоих вариантов угадывания и пользовательских посылок на любом
процессоре. Изменение шаблонов в оптимизации, тестов или определения benchmark меняет конфигурацию
проверки и требует новых замеров. Пакеты без `benchmark` используют максимум по тестам.
Способ измерения берется из `problem.json`; окружение исполнения определяет платформа.

## Загрузка

Backend импортирует задачи при старте и затем раз в `PROBLEMS_SYNC_INTERVAL` (по умолчанию минута).
`PROBLEMS_DIRECTORY` — клон `PROBLEMS_GIT_URL` (в compose — репозиторий задач), перед импортом он
обновляется до `PROBLEMS_GIT_BRANCH`; пакеты лежат в его подкаталоге `PROBLEMS_PATH` (`problems`). Без
`PROBLEMS_GIT_URL` каталог читается как есть. Каждый подкаталог считается пакетом: каталог в чужом формате
не пропускается молча, а попадает в лог как ошибочный пакет. Импорт можно запустить сразу кнопкой на `/admin`.

- Каждое новое содержимое пакета — новая версия задачи. Банк показывает последнюю. Оба условия и шаблоны входят
  в содержимое: правка любого из них даёт новую версию, но не меняет конфигурацию проверки (`judge_hash`), так что
  результаты остаются сравнимыми.
- Контест хранит свою версию каждой задачи: до начала она следует за банком, после начала зафиксирована.
- Пакет с ошибкой не импортируется, в банке остаётся его прежняя версия; причина пишется в лог.
- Пакет, исчезнувший из каталога, уходит из банка, но остаётся в контестах и посылках.
- Генератор и полный `ProblemSpec` хранятся в базе и уходят только судье, клиенту не выдаются.
