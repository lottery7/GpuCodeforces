# Посылки и проверка

## Путь посылки

1. `POST /api/submissions` с процессором и языком проверяет, что задача объявляет этот процессор, платформа
   его предлагает (`PROCESSORS`), язык разрешён, а в контесте процессор совпадает с процессором контеста.
   Посылка сохраняется в статусе `queued` и сразу после коммита уходит в judge gateway
   (`POST {JUDGE_GATEWAY_URL}/api/v1/submissions`, `SubmissionRequest` из `judge-api`): код, полный
   `ProblemSpec` версии задачи с генератором, процессор и язык.
2. Пока gateway не принял посылку (недоступен, 409, 503), она остаётся в очереди: каждые 15 секунд
   backend отправляет её снова. Gateway дедуплицирует по ID, поэтому повтор безопасен. Если за
   `platform.judge.send-timeout` (10 минут) отправить не удалось или gateway ответил 400/413, посылка
   получает `system_error` и автор может повторить проверку.
3. Судья присылает события асинхронно через RabbitMQ, очередь `judge.events`. Backend объявляет её
   с теми же аргументами, что и gateway, поэтому может стартовать первым.
4. Фронтенд опрашивает `GET /api/submissions/{id}`, пока статус не окончательный.

События приходят не по порядку и могут повторяться. Backend учитывает только задание, которое
вернул gateway (`jobId`), применяет события по возрастанию `(attempt, seq)` и не меняет посылку после
`FINISHED`. Ошибка записи события возвращает его в очередь: `judge.events` не теряет сообщения.

| Судья | Статус посылки |
|---|---|
| `QUEUED` | `queued` |
| `COMPILING`, `PREPARING` | `compiling` |
| `TESTING` (с `progress`) | `checking`, `passedTests`/`totalTests` |
| `ACCEPTED` | `accepted`, `score` (значение и тип) по метрике задачи - максимум или геометрическое среднее по тестам - и `metrics` из результата |
| `WRONG_ANSWER` / `TIME_LIMIT_EXCEEDED` / `MEMORY_LIMIT_EXCEEDED` / `RUNTIME_ERROR` | `wrong_answer` / `time_limit` / `memory_limit` / `runtime_error` |
| `COMPILATION_ERROR`, `POLICY_VIOLATION` | `compile_error` |
| `INTERNAL_ERROR`, `CANCELLED` | `system_error` |

`diagnostic` (только автору) собирается из `message`, `compileLog` и первого упавшего теста;
подробности открытых тестов судья уже ограничил примерами.

## Повторная проверка

Только автор и только после `system_error`/`measurement_error`. Код, контекст, версия задачи и время
отправки сохраняются; судье уходит новый ID `<id>.r<n>`, а события старого задания игнорируются.

## Проверка примера

`POST /api/problems/{id}/example` отправляет решение на выбранный процессор с генератором, оставляющим
только тесты `sample: true` (все они считаются замерными: судье нужен хотя бы один замерный тест), и ждёт
вердикта до `platform.judge.example-timeout` (2 минуты). Посылка не создаётся. На процессоре, где у задачи
нет ни одного открытого теста, проверка примера завершится сбоем проверки.
Ответ приходит через ту же очередь событий, поэтому её должен читать один экземпляр backend.

## Результаты

Принятый score сравним только в одной конфигурации проверки и на одном процессоре: тот же `judge_hash` версии
задачи (содержимое `problem.json` + `problem.py`) и тот же процессор. Версии эмуляторов зафиксированы и в
сравнимость не входят. Практика и каждый контест считаются отдельно.

Для задач с benchmark в конфигурацию также входит определение метрики и набора входов.
У оптимизации в нее также входят исходные решения. Рекорды `gpu-cuda` ограничены отпечатком текущей среды:
после смены GPU или переключения между mock и GPU прежние времена не используются для ускорения.
Рекорды эмуляторов отпечатком среды не ограничены: их версии зафиксированы в образах судьи.
Фактические замеры каждого теста сохраняются в `Submission.measurement`; клиент получает только
сводку метрики, режима, числа тестов и модели процессора. `wall` означает весь вызов решения,
а не только время ядер. Схемы и формулы: [formats.md](formats.md).
Эталоны и варианты угадывания автоматически проходят тот же judge отдельными заданиями:
[reference-measurements.md](reference-measurements.md).

- Банк задач: `solved`, `last*` - для пользователя и контекста; `solvedCount` - по всем контекстам; по каждому
  процессору задачи - `bestScore` пользователя и `recordScore` (лучший сравнимый score контекста). Фильтр
  `processor` оставляет задачи, которые можно сдавать на нём; `sort=bestScore` требует процессор.
- Лидеры задачи (`processor` обязателен) - лучший сравнимый score каждого пользователя на процессоре, равные
  делят место.
- Контест проводится на одном процессоре (`processor`, выбирается при создании и меняется только до начала);
  все его задачи должны поддерживать этот процессор, посылки на другой процессор отклоняются. Фильтр
  `processor` в списке контестов.
- Таблица обычного контеста на любом процессоре: число решённых задач, затем меньшее суммарное время сдачи. Задача решена,
  если принята хотя бы одна посылка (верный ответ, score в пределах лимита задачи на процессоре контеста); время
  сдачи - от начала контеста до момента отправки первой принятой посылки (`created_at`), а не до вердикта,
  поэтому очередь и длительность проверки не влияют, повторная проверка время не меняет. Сам score и неверные
  попытки на место не влияют.
- В дуэли сравнивается минимальный score принятого кода общей закрепленной задачи на процессоре комнаты.
  Для GPU сохраняется среда комнаты. Учитываются посылки, отправленные в интервале `[startAt, endAt)`.
  Время отправки не дает преимущества. Сдавшийся проигрывает независимо от прежнего результата.
  Подробнее: [duels.md](duels.md).
- Рейтинг - отдельный на каждый процессор (`user_ratings`, `User.ratings`). Он пересчитывается после окончания
  контеста по месту в таблице (формула в духе Codeforces, изменение не больше +/-400), меняется только рейтинг
  процессора контеста, места пересчитываются внутри процессора. В обычном контесте учитываются только участники,
  отправившие хотя бы одну посылку: регистрация без участия рейтинг не меняет. Расчёт ждёт вердиктов посылок, отправленных до конца,
  но не дольше 30 минут (`RatingFinalizationService.VERDICT_GRACE`); контесты одного процессора обрабатываются в
  порядке окончания, контесты разных процессоров друг друга не ждут. `GET /api/users?sort=rating` требует
  `processor`.
  В дуэли рейтинг получают оба соперника при сдаче или хотя бы одной посылке игрока. Если оба ничего не
  отправили и не сдались, сохраняется ничья без рейтинга. Итоговые места, число решенных задач, значение и тип результата фиксируются
  в JSON-снимке одной транзакцией с рейтингом; поздние вердикты и повторные проверки не меняют итог дуэли.
  При сдаче ожидание проверок не требуется.
- До 5 непроверенных посылок на пользователя (`platform.judge.max-pending-per-user`).

## Процессоры

`PROCESSORS` (`platform.processors.enabled`, по умолчанию `gpu-cuda`) - какие процессоры каталога судьи
предлагает платформа; это тот же список, что `JUDGE_PROCESSORS` у gateway. `platform.processors.models` задаёт,
что показать как модель процессора: для `gpu-cuda` - `GPU_NAME`, для эмуляторов - их закреплённые версии и модель
("Yosys 0.70 + Verilator 5.053", "GPGPU-Sim, NVIDIA Tesla V100 (QV100)"); процессор без модели показывает своё название.
`GET /api/processors` отдаёт включённые процессоры: id, название, модель, языки и тип score. Backend не
опрашивает gateway и не хранит состояние процессоров.

## Логи и зависания

Каждая строка лога backend содержит `[sub=<ID посылки> user=<ник>]`. ID посылки - тот же, что в логах
gateway и executor (у повторной проверки `<id>.r<n>`), поэтому путь одной посылки виден целиком:

```
INFO [sub=98cc... user=admin] SubmissionService : Submission created: problem=vector_add version=... contest=practice processor=gpu-cuda language=cuda
INFO [sub=98cc... user=admin] SubmissionService : Judge gateway accepted 98cc... as job ebf4...
INFO [sub=98cc... user=]      SubmissionService : Status queued -> compiling (judge COMPILING a1/#1 on gpu-node-1)
INFO [sub=98cc... user=]      SubmissionService : Status compiling -> checking (judge TESTING a1/#2 on gpu-node-1)
INFO [sub=98cc... user=]      SubmissionService : Verdict ACCEPTED -> accepted: passed 5/5 ... score=1.73 TIME_MS, judged in 2724 ms on NVIDIA GeForce RTX 3060 (gpu-node-1)
```

- Запросы к API: изменяющие, ошибочные и медленные (от 2 секунд) - INFO/WARN/ERROR с кодом и временем,
  обычные чтения - DEBUG (`LOGGING_LEVEL_DEV_GPUCODEFORCES_BACKEND_COMMON=DEBUG`).
- Gateway недоступен или отклонил посылку - WARN/ERROR с ответом gateway; `system_error` от судьи - ERROR.
- Отброшенные события (старая проверка, чужое задание, повтор после вердикта) и перезапуск задания судьёй
  пишутся с причиной; каждое событие целиком - DEBUG (`LOGGING_LEVEL_DEV_GPUCODEFORCES_BACKEND_SUBMISSION=DEBUG`).
- Ошибка обработки события - ERROR со stack trace, событие возвращается в очередь.
- Непредвиденные исключения в API - ERROR со stack trace, клиенту - только "Внутренняя ошибка сервера".
- **Зависание:** раз в минуту backend ищет посылки, принятые gateway, о которых судья молчит дольше
  `platform.judge.stuck-after` (10 минут), и пишет WARN со статусом, заданием и последним событием.
  Дальше смотрите `GET /api/v1/queues` gateway (есть ли живой executor профиля) и лог executor по ID.

## Администрирование

Администраторы - пользователи с никами из `ADMIN_HANDLES` (через запятую). Страница `/admin`
выполняет Groovy-скрипты в работающем приложении (`ctx` - Spring `ApplicationContext`, `out` - вывод)
и запускает импорт задач. Это полный доступ к процессу: один скрипт одновременно, таймаут 30 секунд,
в лог пишутся автор и SHA-256 скрипта. API: `POST /api/admin/console`, `POST /api/admin/problems/sync`.

В Groovy-консоли код и результат стоят рядом, на узком экране результат идет под кнопкой.
Длинные результаты и вывод прокручиваются внутри своих областей. Статус виден рядом с кнопкой,
повторный запуск заблокирован до ответа; новый результат вне экрана показывается ближайшей прокруткой.

```groovy
ctx.getBean('submissionService').resendUnsent()
```
