# Проверка планов PostgreSQL в тестах

Проверка подключается автоматически ко всем Spring-тестам через
`backend/src/test/resources/META-INF/spring.factories`. Тестовый DataSource
перехватывает SQL приложения, включая запросы из HTTP-обработчиков, фоновых потоков,
обычных Statement, PreparedStatement и их batch-вариантов.

В начале тела каждого теста включается сбор, в конце сохраняется отчёт и проверяются
нарушения. Проверяются выполненные ветви кода, не все теоретически возможные SQL.
Подготовка данных в `@BeforeEach`, прямые SQL-утверждения из тестов и DDL не являются
прикладной нагрузкой. Они не проверяются. Прямые соединения вне Spring DataSource
также не перехватываются; тесты самой обвязки явно включают для них `checkFixture`.
Тесты не должны выполняться параллельно в одном JVM; настройка закреплена в Gradle.

```sh
./gradlew :backend:integrationTest
```

Выполнение теста падает при неожиданном полном обходе, даже если приложение само
перехватило SQL-ошибку. Отчёты: `backend/build/reports/query-plans/*.jsonl`.
Каждая запись содержит SQL с параметрами, место вызова, обычный план, при необходимости
диагностический план и обоснования исключений. Структура плана сохраняется,
но выражения с подставленными значениями заменяются признаками наличия условий:
токены сессий, пароли и остальные значения параметров в отчёт не попадают.

## Что считается нарушением

- `Seq Scan`, в том числе параллельный, и `Sample Scan` по прикладной таблице.
- `Index Scan` / `Index Only Scan` без `Index Cond`: замена полного обхода таблицы
  полным проходом по индексу сама по себе не решает проблему.
- Полный `Bitmap Index Scan` без индексного условия.

Последовательное чтение маленькой таблицы PostgreSQL часто выбирает обоснованно,
даже при наличии хорошего индекса. Поэтому для неожиданного обычного плана
проверяется альтернативный план с локальным `enable_seqscan=off`. Исключение
для маленьких тестовых данных разрешается только при двух условиях: heap таблицы
занимает не больше 64 KiB и альтернативный план действительно устраняет полный
обход. Без подходящего индекса тест падает и на двух строках.

Эта настройка применяется только к диагностическому EXPLAIN. Она откатывается
до выполнения настоящего запроса; обычный план не подменяется принудительно
индексным. Используется EXPLAIN без ANALYZE: INSERT/UPDATE/DELETE не исполняются
повторно. Текущая транзакция, её изменения и настройки планировщика сохраняются
через savepoint. Это отдельно проверяется тестами.

Индексный проход непосредственно под LIMIT разрешается без `Index Cond`, если нет
фильтра: чтение первых элементов упорядоченного индекса не требует его полного
обхода. LIMIT над сортировкой, агрегированием или фильтрацией такого разрешения
не даёт. Сканирование CTE и промежуточных результатов не считается чтением
физической таблицы.

Системные каталоги PostgreSQL и история Flyway отмечены как инфраструктура.
Таблицы `runtime_settings`, `github_budget`, `admin_bootstrap` допускают не больше
одной строки благодаря `PRIMARY KEY(singleton)` и `CHECK(singleton)`; их чтение
имеет постоянную стоимость. Обоснование также включается в отчёт.

## Где задаются намеренные обходы

У конкретного SQL-запроса ставится метка:

```sql
/* full-scan:rating-rebuild */
DELETE FROM rating_event
```

В `QueryPlanGuard.kt`, в реестре `policies`, этой метке соответствует объяснение
и точный набор допустимых таблиц. Для очереди и пула дополнительно фиксируются
имена разрешённых частичных индексов. Нельзя разрешить обход произвольной таблицы,
просто дописав комментарий: неизвестная метка или другая таблица приводит к ошибке.

| Метка | Что разрешено и почему |
|---|---|
| `rating-rebuild` | Полный пересчёт рейтинга и мест после позднего результата. Требуются все завершённые соревнования и рейтинговые события; обновляются все затронутые пользователи. |
| `user-directory` | Точный размер каталога пользователей и поиск произвольной подстроки, включая пустые и короткие запросы. В этой модели нет отдельного счётчика или поискового индекса. История рейтинга не читается. |
| `catalog` | Точный размер доступного банка и полный набор его тем. Разрешены только таблицы источников; история версий и посылок не исключаются из проверки. Текущие версии читаются по PK. |
| `repository-reconciliation` | Сверка всей доступной установки GitHub с прежним набором репозиториев и отключение удалённых. Список ограничен `max-repositories`; по умолчанию 100, максимум настройки 10000. |
| `inflight-count` | Точная вместимость очереди требует пересчитать незавершённые посылки. Разрешён полный проход только по частичным индексам `submission_inflight_worker` / `submission_inflight_user`; история и большие Seq Scan не разрешены. |
| `worker-pool` | Диспетчеру нужен весь активный пул, не более 32 настроенных тестировщиков. Разрешён проход только по частичному `judge_worker_alive`, исключающему неактивную историю. |

Это сознательные линейные операции, а не утверждение, что их нельзя оптимизировать
никакой архитектурой. Например, каталоги и фасеты можно материализовать отдельно.
Для текущего контракта выбран точный результат и явное ограничение источников.
Профиль пользователя к исключениям не относится: готовые рейтинг и место сохраняются
при пересчёте и читаются по ключу пользователя.

Добавляя исключение, нужно указать причину и минимальный набор таблиц/индексов
в реестре, поставить метку у SQL и обновить эту таблицу. Расширение JOIN на другую
неиндексированную таблицу не становится разрешённым автоматически.

## Пределы проверки

EXPLAIN проверяет видимый план SQL на тестовых данных и текущих параметрах. Он
не заменяет нагрузочные тесты и анализ планов на производственной статистике.
Он также не раскрывает внутренние запросы триггеров и пользовательских SQL-функций
и не проверяет кэшированные generic plans production-соединений. CALL/DO отклоняются
как неподдерживаемый для такой проверки процедурный SQL.

Саму проверку покрывают регрессионные тесты: отсутствие/добавление индекса,
маленькие таблицы, полные индексные проходы, границы исключений, batch-запросы,
сохранение транзакции и отсутствие значений параметров в отчёте. Их отчёты с
префиксом `GuardRegression` могут содержать ожидаемые нарушения: JUnit проверяет,
что обвязка их действительно отклоняет.

Основания: [EXPLAIN в PostgreSQL](https://www.postgresql.org/docs/18/using-explain.html)
и [ограничения enable_seqscan](https://www.postgresql.org/docs/18/runtime-config-query.html).
