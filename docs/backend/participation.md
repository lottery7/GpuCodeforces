# Дорешивание, виртуальное участие и взломы

## Контексты отправок

`context` определяет версию задачи и область зачёта:

| Значение | Режим |
|---|---|
| `practice` | Общая практика, текущая опубликованная версия задачи |
| UUID контеста | Официальное участие, закреплённая версия задачи |
| `upsolve:UUID-контеста` | Дорешивание закреплённой версии на итоговых тестах |
| `virtual:UUID-попытки` | Виртуальное участие на итоговых тестах исходного контеста |

Контекст передаётся в запросах задач, примеров, лидеров и истории отправок.
В `POST /submissions` можно передать `context`; старый `contestId` продолжает
означать официальное участие. Если указаны оба поля, контест должен совпадать.
Ответ отправки содержит `context` для построения ссылок.

Официальные, виртуальные результаты и дорешивание считаются отдельно. В общем
счётчике решённых задач учитываются все режимы. Дорешивание и виртуальное участие
открываются после окончательной обработки контеста и не изменяют рейтинг.
Задачи во всех режимах контеста сдаются на его процессоре. Ответ в задаче на
угадывание даётся один раз в каждом контексте.
Общая практика продолжает проверять актуальный пакет; дополнительные тесты
архивного контеста автоматически не меняют пакет в репозитории задач.

Для дуэлей дорешивание, виртуальное участие и взломы закрыты. После завершения задача доступна в обычной практике.

## Виртуальное участие

- `POST /contests/{id}/virtual` создаёт попытку длительностью исходного контеста.
- Повторный запрос возвращает уже активную попытку этого контеста. Пока есть
  активная попытка другого контеста, новую начать нельзя.
- `GET /virtual` возвращает собственную историю, `GET /virtual/{id}` — состояние
  попытки, серверное время и результаты. Чужие попытки и их отправки закрыты.
- Сервер проверяет дедлайн при сохранении отправки. Вовремя принятый код
  учитывается и при получении вердикта после дедлайна. Паузы нет.
- После окончания можно начать новую независимую попытку либо дорешивать.

Версии задач, итоговые тесты и процессор наследуются от исходного контеста.
Результат попытки считается как строка таблицы контеста: число решённых задач и
время сдачи каждой — от начала попытки до отправки первой принятой посылки
(`solved`, `totalSeconds`, `times`). Дуэль виртуально пройти нельзя.

Во время активной попытки авторизованному участнику не раскрывается чужой
конкурсный код. Общедоступный архив можно прочесть заранее или без входа;
виртуальное участие не является защищённым экзаменом.

## Период взломов

Автор контеста задаёт `hackDurationMinutes`: от 0 до 10080 минут после `endAt`.
Ноль отключает взломы. Настройку можно менять до начала контеста.
После окончания приёма решений конкурсные исходники публикуются. Проверка взлома
доступна после завершения текущих проверок официальных отправок.

`POST /hacks` принимает `submissionId` чужого принятого официального решения и
`testJson`. Формат входного теста:

```json
{"scalars":{"N":2},"inputs":{"A":[1,2],"B":[3,4]}}
```

Имена и типы соответствуют сигнатуре `solve`. Передаются все `INPUT` и начальные
значения `INOUT`; ответ вычисляет авторский `reference`. Другие поля, включая
`expected` и исходный код генератора, не принимаются. Взлом проверяется на
процессоре и языке взламываемого решения. Ответ в задаче на угадывание взломать
нельзя: в нём нет кода.

Ограничения первой версии:

- не более 64 КБ JSON и 8192 входных элементов суммарно;
- размер каждого массива, включая выходные, от 1 до 8192 элементов;
- только конечные числа, целые значения должны помещаться в свой тип;
- не более 32 различных кандидатов тестов на задачу контеста;
- не более двух ожидающих проверки взломов от пользователя в одном контесте;
- успешны неверный ответ и ошибка выполнения; взломы по времени и бонусные баллы
  за взломы не поддерживаются.

Повтор одного теста против той же отправки возвращает существующую запись.
Тот же вход можно проверить против другого решения. Одинаковые успешные тесты
в итоговом наборе не дублируются.

`GET /hacks?contestId=...` возвращает историю. Состояния: `queued`, `successful`,
`unsuccessful`, `invalid`, `system_error`. После системного сбоя автор может
вызвать `POST /hacks/{id}/retry`, в том числе после закрытия периода. При повторе
используется новый идентификатор задания, события предыдущего игнорируются.

## Требования к задаче

Для взломов пакет должен содержать `allowCustomTests: true`, а Python-модуль —
функцию `validate_input(test, inputs)`. Она получает копии входных тензоров и
возвращает именно `True` для допустимого теста и `False` для недопустимого.
Проверять нужно ограничения условия: диапазоны, структуру матриц, сортировку
и прочие свойства. Исключение в валидаторе считается ошибкой задачи, а не
успехом или неудачей участника. Пример есть в `judge/problems/examples/vector_add`.

Пользовательские тесты готовятся в песочнице. Ответы не монтируются в процесс
решения. Проверка выполняется с исходным checker и допусками. Дополнительные
тесты идут без замера на любом процессоре задачи: в score посылки они не входят
и лимитом score не ограничены; защитные лимиты процессора остаются.
Существующее ограничение доверия к времени внутри процесса решения описано
в `judge/README.md` и этим изменением не устраняется.

## Перетестирование и окончательные результаты

Успешный взлом расширяет набор тестов задачи. Фоновый обработчик перетестирует
все ранее принятые официальные отправки, включая запасные решения участника.
Одновременно планируется не больше двух ожидающих перетестирований; остальные
подхватываются следующими итерациями. Тесты передаются судье через существующую
очередь процессора контеста. Отдельной гарантии приоритета над другими видами заданий нет.

Наборы дополнительных тестов неизменяемы и хранятся один раз по SHA-256 в
`test_suites`. Отправка хранит идентификатор использованного набора. Перед новой
проверкой её прежний результат сохраняется в `judging_runs`. Если во время
проверки появился ещё один успешный тест, принятое решение будет проверено
на новом наборе следующей итерацией. Перезапуск backend не теряет эту работу.
Список тестов процессора в блоке «Среда» задачи пополняется только проверками
без дополнительных тестов.

Рейтинг применяется только после закрытия периода взломов, проверки всех
взломов в очереди и перепроверки официальных решений на актуальных наборах:
эту работу платформа делает сама, и её результата ждут всегда. Проверки,
упавшие в судье (`system_error`, `measurement_error` посылки или `system_error`
взлома), и посылки без вердикта ждут повтора не дольше 30 минут после срока
результатов и последнего события судьи; затем результаты фиксируются без них.
Причина ограничения: рейтинги одного процессора применяются по порядку срока
результатов (конец периода взломов, без него — конец контеста), и ожидающий
контест задерживает следующие. Уже окончательные официальные результаты
пользователь перепроверить не может. Дорешивание и виртуальные попытки
используют замкнутый итоговый набор тестов.

Миграция сохраняет опубликованные результаты старых контестов: контест с
применённым рейтингом считается окончательно завершённым.
