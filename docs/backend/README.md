# Backend

## Запуск и конфигурация

Нужны JDK 26, PostgreSQL 18 и работающий Docker для интеграционных тестов.

```sh
docker compose up -d --wait
SECURE_COOKIES=false ./gradlew :backend:bootRun
```

Адрес API — `http://localhost:8080/api`, health — `/actuator/health`.
`DATABASE_URL`, `DATABASE_USER`, `DATABASE_PASSWORD` переопределяют подключение.
Значения по умолчанию предназначены для локальной разработки.
В публичной среде нужны HTTPS, `SECURE_COOKIES=true` и точный `PUBLIC_ORIGIN`
без завершающего `/`. По умолчанию origin клиента — `http://localhost:5173`.
Клиент и API должны иметь общий origin; Nginx frontend перенаправляет `/api/`.

Дополнительный YAML можно подключить через
`SPRING_CONFIG_ADDITIONAL_LOCATION=file:/path/to/platform.yaml`.
Доступны обычные свойства Spring Boot, например `platform.judge.timeout` в YAML
и `PLATFORM_JUDGE_TIMEOUT` в окружении.
Без GitHub App банк пуст, без подходящего настроенного тестировщика отправка
решения получает `503`.

## Импорт задач через GitHub App

Приложению нужны права **Contents: read**, **Metadata: read**. После установки
в репозитории задайте `GITHUB_APP_ID` и `GITHUB_APP_PRIVATE_KEY_FILE`.
Ключ должен быть RSA PKCS#8 PEM без шифрования. Ключ PKCS#1 преобразуется локально:

```sh
openssl pkcs8 -topk8 -nocrypt -in github-app.pem -out github-app.pkcs8.pem
```

Ключ нельзя добавлять в репозиторий. Backend использует
[JWT GitHub App](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app)
и [installation access token](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation).

Используется опрос, webhook не требуется. Установки и репозитории обнаруживаются
каждые 10 минут, конкретный репозиторий проверяется не чаще раза в 2 минуты.
Всегда читается `master`, независимо от default branch. ID новой задачи имеет вид
`ID_репозитория:ключ_задачи`; переименование репозитория или перенос файлов не меняет ID.
Установка приложения означает публикацию задачи в общем банке, даже если исходный
репозиторий приватный. Репозиторий может содержать несколько задач.

В корне `master` нужен `index.json`:

```json
{
  "tasks": [
    {"id": "vector-add", "manifest": "tasks/vector-add/task.json"},
    {"id": "reduction", "manifest": "tasks/reduction/task.json"}
  ]
}
```

`id` — устойчивый ключ из 1–64 латинских букв, цифр, `_` и `-`, уникальный внутри
репозитория. `manifest` — путь от корня репозитория. Изменение ключа создаёт другую
задачу; изменение пути при прежнем ключе сохраняет её идентичность.
Пустой `tasks` допускается и убирает задачи репозитория из банка.

Каждый манифест содержит метаданные и пути к файлам, также **от корня репозитория**:

```json
{
  "code": "A",
  "title": "Сложение векторов",
  "difficulty": "easy",
  "tags": ["CUDA", "Векторы"],
  "statement": "tasks/vector-add/statement.md",
  "starter": "tasks/vector-add/starter.cu",
  "generator": "shared/generator.cpp",
  "referenceSolution": "tasks/vector-add/reference.cu",
  "environment": "shared/environment.md",
  "environmentId": "a100-cuda13",
  "testCount": 20,
  "timeLimitSeconds": 2.0,
  "memoryLimitMb": 1024,
  "referenceTimeMs": 10.0,
  "absoluteTolerance": 0.000001,
  "relativeTolerance": 0.000001
}
```

Файлы — обычные UTF-8, пути относительные, ссылки и подмодули вместо файлов
не допускаются. `statement.md` содержит условие, формат ввода/вывода и примеры,
`environment.md` — оборудование и методику измерения. Генератор и решения —
исходные тексты самостоятельных программ, подробнее в [протоколе](judge-protocol.md).
`testCount` — от 1 до 10000. `referenceTimeMs` — эталонная сумма времени всех тестов.
По умолчанию `environmentId=default`, допуски — `1e-6`.

Версия — SHA commit. Импорт всех задач из индекса атомарен: ошибка хотя бы одной
не заменяет предыдущий набор и не удаляет остальные задачи. Причина отказа хранится
в `source_repository.error`. Удалённая из индекса задача исчезает из банка,
но остаётся в истории соревнований и посылок. Возврат к прежнему commit
восстанавливает соответствующий ему набор задач без создания повторных версий.
Миграция сохраняет ID ранее импортированных задач. Чтобы продолжить такую задачу,
используйте ключ `legacy` в индексе её репозитория; прочие ключи создают новые задачи.
Условия, шаблон, генератор и эталон сохраняются в PostgreSQL. Последние два
не выдаются клиентскому API. Backend не запускает код репозитория.

Соревнование фиксирует версии при создании, посылка — при отправке. При редактировании
соревнования уже включённые задачи сохраняют версии, добавленные берутся из банка.
Удаление установки/репозитория исключает задачу из банка после успешного обнаружения,
но не удаляет историю. В API задачи добавлены `revision`, `testCount`,
в детали посылки — `revision`, `testResults` с вердиктами отдельных тестов.

## Ограничения импорта

| Параметр `platform.github.*` | По умолчанию |
|---|---:|
| `max-installations` | 20 |
| `max-repositories` | 100, включая сохранённые отключённые репозитории |
| `max-repositories-per-installation` | 20 |
| `discovery-interval` / `repository-interval` | `10m` / `2m` |
| `max-requests-per-minute` | 120 для всех экземпляров backend в одной БД |
| `max-repository-bytes` | 20 MiB |
| `max-tree-entries` | 2000 |
| `max-file-bytes` | 128 KiB |
| `max-package-bytes` | 512 KiB на задачу с её манифестом |
| `max-tasks-per-repository` | 100 в одном индексе |
| `max-stored-tasks-per-repository` | 500 разных ключей с учётом истории |
| `max-imported-bytes-per-repository` | 4 MiB на весь импорт, включая индекс |
| `max-stored-bytes-per-repository` | 64 MiB сохранённых JSON-данных всех версий |
| `max-api-response-bytes` | 1 MiB |
| `max-versions-per-repository` | 100 |
| `http-timeout` | `10s`, включая чтение тела |

Превышение числа установок/репозиториев отклоняет обнаружение целиком, без подмены
полного списка частичным. Большие репозитории отключаются по метаданным GitHub;
размер дерева commit проверяется дополнительно. Усечённые деревья отклоняются.
Репозитории не клонируются, история Git не скачивается. Проверяются SHA blob.
Backend не следует перенаправлениям и не обращается к URL из манифеста.
Учитываются ограничения GitHub и `Retry-After`. Частота commit не ускоряет опрос.

Общие файлы скачиваются один раз за импорт, но учитываются в бюджете каждой задачи,
которая их использует. Поэтому общим генератором нельзя обойти ограничение объёма
сохранённых данных. Лимит версий считается по commit репозитория, а не по числу задач.
При достижении лимита версий, накопленных ключей или объёма импорт останавливается: история автоматически
не удаляется ради новых обновлений. Администратор должен пересмотреть лимит
или политику хранения. Обнаружение и импорт координируются арендой в PostgreSQL.

## Тестировщики и очередь

```yaml
platform:
  judge:
    max-in-flight: 2
    timeout: 5m
    max-attempts: 5
    ping-interval: 30s
    ping-timeout: 10s
    http-timeout: 5s
    inbox-capacity: 10000
    workers:
      - id: gpu-1
        url: https://judge-1.example.org
        token: ${JUDGE_ONE_TOKEN}
        environment-id: a100-cuda13
```

Ключ — случайная строка не короче 32 символов, отдельная для каждого сервиса.
Адреса задаёт администратор; участник не может добавить адрес назначения.
Тестировщики должны иметь доступ к обратным URL backend.
Все задачи соревнования должны иметь одинаковый `environmentId`.

Назначения и результаты хранятся в БД и переживают перезапуск. Между экземплярами
backend используются блокировки PostgreSQL. На тестировщика отправляется от одной
до трёх незавершённых посылок. Остальные ждут в локальной БД. При таймауте попытки
тестировщик исключается, частичные результаты удаляются, работа возвращается
в очередь с новым `attemptId`. После предельного числа попыток — `system_error`.
Старые ответы игнорируются. Между подтверждением приёма задания и новым результатом,
а затем между новыми результатами тестов не должно проходить больше `timeout`.

Живость подтверждают успешный HTTP-ответ на приём посылки, корректный результат
актуальной попытки или обратный pong с актуальным nonce. Ответ о посылке сбрасывает
ожидание pong и откладывает следующий ping. Повтор результата подтверждает связь,
но не продлевает срок проверки этой посылки. При переполнении буфера корректный
ответ также подтверждает живость, хотя его доставку нужно повторить после `503`.
Для первоначальной активации без назначенных посылок нужен обратный pong.
Мёртвые продолжают получать ping. Если все подходящие тестировщики мертвы,
посылки ждут в БД. Протокол отмены старого выполнения пока отсутствует;
доставка допускает повторы. Подробнее: [judge-protocol.md](judge-protocol.md).

Обратный запрос результата только проверяет данные и сохраняет их в ограниченную
таблицу `judge_inbox`. После `202` данные уже в PostgreSQL. Фоновый обработчик
переносит результаты в `test_result` и вычисляет итог по порядку тестов.
При заполнении буфера возвращается `503`, нужен повтор с задержкой.

Проверка примера требует входа, использует ту же очередь, но не попадает в историю
и рекорды. Одновременно ответа ожидают не больше 16 HTTP-запросов на процесс,
не дольше `platform.judge.example-wait` (по умолчанию `10s`). После `504` проверка
может завершиться позже, без публикации как обычной посылки.

## Остальные ограничения и безопасность

| Параметр `platform.*` | По умолчанию |
|---|---:|
| `requests-per-minute` / `auth-requests-per-minute` | 300 / 15 на IP и процесс |
| `max-rate-limit-keys` | 10000 |
| `max-body-bytes` | 256 KiB; обратные запросы — 16 KiB |
| `max-code-bytes` | 128 KiB |
| `max-queued-submissions` | 10000 незавершённых посылок |
| `max-pending-per-user` | 10, включая примеры |
| `session-ttl` | `7d` |

Для обратных запросов с действующим ключом действует отдельный лимит
`platform.judge.callback-requests-per-minute`: 30000 на тестировщика и процесс.

Пароли — PBKDF2-HMAC-SHA256, отдельная соль, 210000 итераций. В БД хранятся
SHA-256 случайных токенов сессии. Cookies: HttpOnly, SameSite=Lax, Secure
по умолчанию. Изменяющие запросы клиента требуют точного `Origin`.
Внутренние запросы используют отдельные ключи. Проверяется размер тела
и без `Content-Length`. Исходники и диагностика доступны только автору посылки.

Это ограничения приложения, а не защита сетевого канала от объёмной DDoS-атаки.
На входном прокси нужны лимиты соединений, времени чтения и общего потока запросов.
Приложение использует непосредственный адрес клиента и не доверяет произвольному
`X-Forwarded-For`; за прокси ограничения по клиентским IP настройте на самом прокси.
Ограничители частоты находятся в памяти процесса; лимиты очереди, назначений
и буфера общие для экземпляров backend в одной БД.

## Администрирование

Страница `/admin` обслуживается самим backend и доступна также через Nginx и Vite
клиента. Вход использует обычную сессию приложения; разрешение проверяется по
`app_user.is_admin` на каждом админском запросе. Публичная регистрация не даёт роли
администратора. Изменяющие запросы требуют того же `PUBLIC_ORIGIN`, что и остальной API.
При открытии напрямую на `http://localhost:8080/admin` для локальной разработки
укажите `PUBLIC_ORIGIN=http://localhost:8080` и `SECURE_COOKIES=false`.

Первый администратор:

1. Создайте обычный аккаунт приложения.
2. Задайте при запуске `ADMIN_BOOTSTRAP_TOKEN` — случайный секрет не короче 32 символов.
   Для генерации можно использовать `openssl rand -hex 32`.
3. Войдите в этот аккаунт на `/admin` и введите секрет первоначальной настройки.

Назначение выполняется один раз для БД и записывается в `admin_bootstrap`.
Другой пользователь не может повторно получить права этим секретом.
После назначения секрет можно убрать из окружения. Без секрета первоначальное
назначение через HTTP отключено. Дополнительные роли можно назначать из консоли:

```groovy
def db = ctx.getBean('database')
db.update('UPDATE app_user SET is_admin = true WHERE id = ?', 'user-uuid')
```

Groovy-консоль выполняет скрипт с настоящим Spring `ApplicationContext` в `ctx`.
Доступны бины и рефлективный доступ Groovy к их внутреннему состоянию.
`println`/`out` выводятся отдельно от возвращаемого значения.
Ошибки компиляции и исполнения возвращаются как ошибки консоли (`422`).

```groovy
println ctx.getBean('runtimeSettings').current()
return ctx.beanDefinitionNames.sort().join('\n')
```

Это полный административный доступ к процессу, а не изолированная среда исполнения.
Один скрипт на экземпляр backend, исходник до 64 KiB, вывод до 65536 символов,
ожидание по умолчанию 30 секунд (`platform.admin.console-timeout`).
По таймауту возвращается `504` и отправляется прерывание. Groovy-код может его
игнорировать; до фактического завершения новый скрипт не запускается.
На время выполнения служебные потоки и ресурсы, созданные самим скриптом,
остаются ответственностью администратора. Скрипты и вывод не сохраняются в журнал:
`admin_audit` содержит автора, действие, время и SHA-256 исходника.

### Настройки без перезапуска

На той же странице редактируются:

- частота обычных запросов, входа и обратных запросов тестировщиков;
- общий размер очереди и число незавершённых посылок пользователя;
- число одновременных назначений тестировщику, таймаут и число попыток;
- вместимость буфера результатов, интервалы ping/pong и ожидание примера;
- интервалы обнаружения/проверки репозиториев и частота запросов к GitHub.

Значения сохраняются в `runtime_settings`, после сохранения имеют приоритет
над соответствующими значениями YAML и переживают перезапуск. На текущем экземпляре
применяются сразу, на остальных — в течение секунды. Для конкурентного редактирования
используется номер версии; устаревшая запись получает `409` и не затирает новую.
Недопустимые значения отклоняются целиком (`400`).

Изменения относятся к новым назначениям и запросам: текущие задания сохраняют
свои сроки. Уменьшение лимита не удаляет посылки или результаты, уже находящиеся
в очереди/буфере. Ранее назначенные задания сверх нового лимита завершаются,
новые не выдаются до освобождения мест. При уменьшении интервалов ближайшие
обнаружение и ping сдвигаются раньше.

Секреты, адреса тестировщиков, `PUBLIC_ORIGIN`, cookies, подключения, HTTP-клиенты,
пределы размеров файлов и данных, а также настройки самой консоли меняются через
конфигурацию запуска и требуют перезапуска. Страница не выдаёт их значения.

Админские операции: `GET /api/admin/access`, `POST /api/admin/bootstrap`,
`POST /api/admin/console`, `GET /api/admin/settings`, `PUT /api/admin/settings`.
Последние три требуют роли администратора. Ответ настроек содержит `{version, values}`;
сохранение принимает тот же объект. Изменения настроек и запуски консоли аудируются.

## Результаты и рейтинг

Практика и соревнования имеют отдельные рекорды. Только результаты той же версии
задачи участвуют в текущих рекордах. Время задачи — сумма времени тестов.
Места в соревновании определяются числом решённых задач, затем суммой отношений
эталонного времени к лучшему времени участника. Равные результаты делят место.

После завершения соревнования и его незавершённых проверок рассчитывается рейтинг:
попарная формула Elo, начальное значение 1500, коэффициент 32, среднее по соперникам.
Учитываются участники, отправлявшие решения. У единственного участника изменение 0.
После поздней повторной проверки рейтинг пересчитывается по хронологии соревнований.
Призов, дисквалификаций, административной модерации и выбора GPU участником нет.

## Проверки

```sh
./gradlew test
./gradlew :backend:integrationTest
./gradlew build
./gradlew :backend:openApiValidate :backend:verifyOpenApiGenerated
```

Интеграционные тесты требуют Docker и используют отдельный PostgreSQL 18.1
через Testcontainers. Они проверяют HTTP API, очередь, буфер результатов,
таймауты и восстановление тестировщика, доступ к исходникам, версии соревнований
и рейтинг. Модульные тесты проверяют ограничения импорта и HTTP-запросов.
Клиентские тесты запускаются отдельно в `frontend`.

В каждом Spring-тесте автоматически проверяются планы прикладных SQL-запросов.
Неожиданные полные обходы завершают тест ошибкой. Намеренные обходы отмечаются
у SQL и имеют явное обоснование и границы в тестовом реестре.
Подробности и отчёты: [проверка планов PostgreSQL](query-plans.md).
