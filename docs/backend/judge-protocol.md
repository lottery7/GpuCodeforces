# Протокол backend — тестировщик, версия 1

Тестировщик — отдельный доверенный сервис. Backend не выполняет и не компилирует
решения, генераторы и эталоны. Каждый тестировщик самостоятельно изолирует
недоверенный код, ограничивает ресурсы и исключает доступ участника к эталону.

Все запросы JSON по HTTPS; локально допустим HTTP. В обоих направлениях:
`Authorization: Bearer <token>` с отдельным ключом сервиса из конфигурации.
Тестировщик знает собственный ID и внешний базовый адрес backend из своей настройки.

## Отправка задания

Backend вызывает `POST {worker.url}/tasks`:

```json
{
  "submissionId": "7cda76af-d9bd-4f25-b3db-0c235eb51602",
  "attemptId": "a39527f6-a5fe-40d2-8dde-d7b12dfe408e",
  "participantId": "participant-id",
  "problemId": "123456",
  "revision": "0123456789012345678901234567890123456789",
  "code": "исходный код участника",
  "generator": "исходный код генератора",
  "referenceSolution": "исходный код эталона",
  "testCount": 20,
  "timeLimitSeconds": 2.0,
  "memoryLimitMb": 1024,
  "environmentMarkdown": "NVIDIA A100, CUDA 13; описание замера",
  "mode": "submission",
  "environmentId": "a100-cuda13",
  "absoluteTolerance": 0.000001,
  "relativeTolerance": 0.000001
}
```

Ответ `2xx` означает приём задания во внутреннюю очередь. Тело не требуется
и ограничено 4 KiB. Повторный приём `(submissionId, attemptId)` не должен запускать
второе выполнение. Новый `attemptId` — новая попытка. Посылка занимает место
до окончательного результата или таймаута попытки.

В `mode=example` передаётся `testCount=1`, генератор выдаёт пример из условия.
В `mode=submission` генерируется полная серия тестов.

Интерфейс исходников для совместимого тестировщика:

- Генератор — самостоятельная программа C++, принимает аргументы
  `mode`, `testNumber`, `seed` и пишет входные данные в stdout.
- Эталон и решение участника — самостоятельные программы C++/CUDA, читают stdin
  и пишут ответ в stdout. Шаблон содержит необходимую обвязку.
- Номера тестов начинаются с 1. Seed — первые 16 шестнадцатеричных символов
  SHA-256 UTF-8 строки `revision:testNumber`, переданные как строка;
  генератор разбирает её как uint64. Это обеспечивает воспроизводимость.
- Сравниваются разделённые пробелами токены. Числовые токены сравниваются по
  `abs(actual - expected) <= absoluteTolerance + relativeTolerance * abs(expected)`,
  остальные — точно. NaN/Infinity не являются допустимыми числами.
- `environmentId` определяет согласованные GPU, компилятор и методику измерения.
  Задание назначается только тестировщику с тем же ID среды.
  Markdown поясняет среду, но не является исполняемой командой.

Исполнение этого контракта обеспечивает внешний тестировщик. Изменение
оборудования или методики требует нового ID среды и commit задачи.

## Результат теста

Тестировщик вызывает `POST {backend}/api/internal/judges/{workerId}/results`:

```json
{
  "submissionId": "7cda76af-d9bd-4f25-b3db-0c235eb51602",
  "attemptId": "a39527f6-a5fe-40d2-8dde-d7b12dfe408e",
  "testNumber": 1,
  "verdict": "accepted",
  "timeMs": 0.125,
  "diagnostic": ""
}
```

Вердикты: `accepted`, `compile_error`, `wrong_answer`, `runtime_error`, `time_limit`,
`memory_limit`, `system_error`, `measurement_error`. Для `accepted` обязательно
конечное `timeMs` от `1e-9` до `1e12` мс. Для остальных время может отсутствовать или быть
`null`. Диагностика ограничена 8 KiB; весь обратный запрос — 16 KiB.

Результаты можно присылать не по порядку. Backend сохраняет их в ограниченную
таблицу `judge_inbox` и отвечает **202 до вычисления итогового состояния**.
Отдельный обработчик переносит их в `test_result` и обновляет посылку.
После `202` результат сохранён в PostgreSQL.

Повторы не создают повторных результатов. Конфликтующие сообщения одного теста
ещё в буфере получают `409`; обработанный тест не перезаписывается. Ответ от старой
попытки или после завершения посылки получает `202` и игнорируется. При заполнении
буфера возвращается `503`: нужен повтор с задержкой. При сетевом сбое или `5xx`
тестировщик также повторяет запрос.

Первая ошибка по порядку тестов становится итогом после получения всех предыдущих
результатов. Можно остановиться на первой ошибке, но нужно прислать результаты
предшествующих тестов. Ошибку компиляции или сбой до первого теста нужно прислать
для теста 1. После всех успешных тестов итог — `accepted`, время — сумма `timeMs`.

Клиентская деталь посылки содержит `testResults`: номера, вердикты, время.
Диагностика и код выдаются только автору, генератор и эталон никогда не выдаются.

## Таймаут и повторное назначение

`platform.judge.timeout` ограничивает ожидание нового результата посылки. Срок
начинается при назначении, обновляется после успешного подтверждения приёма задания
и после каждого нового корректного результата теста. Повтор уже полученного
результата не продлевает срок посылки. Настройка должна покрывать генерацию,
компиляцию и максимальную паузу между новыми результатами, а не время всей серии.

При таймауте или неуспешной отправке тестировщик исключается из активного пула,
его незавершённые назначения возвращаются в очередь. Частичные результаты
удаляются, новая попытка получает новый `attemptId`. На следующем проходе
диспетчера работу получает свободный активный тестировщик нужной среды.

После `max-attempts` получается `system_error`. Автор может запросить повторную
проверку через клиентский API: ID, код, версия, контекст и время отправки сохраняются,
счётчик попыток начинается заново.

Доставка допускает повторы. После сетевого разрыва старый тестировщик может
продолжать вычисление, его ответ после смены попытки не учитывается.
Тестировщику нужен собственный конечный срок выполнения задания.
Протокол отмены старого выполнения пока отсутствует.

## Ping/pong

Backend периодически вызывает `POST {worker.url}/ping`:

```json
{"nonce":"a39527f6-a5fe-40d2-8dde-d7b12dfe408e"}
```

Тестировщик отвечает `2xx` и отдельным запросом вызывает
`POST {backend}/api/internal/judges/{workerId}/pong` с тем же телом и ключом.
Backend отвечает `204`. Актуальный `nonce` до истечения срока подтверждает живость.
Просроченный или повторный pong не восстанавливает доступность.

Живость также подтверждают успешный HTTP-ответ на приём задания и корректные
обратные запросы о тестах актуальной попытки, включая повторы. Они сбрасывают
ожидание pong и откладывают следующий ping. При заполнении буфера корректный
результат подтверждает живость даже при ответе `503`; результат нужно прислать снова.
Неверные данные, ответы от другого тестировщика и устаревшие попытки живость
не подтверждают. Обычного HTTP-ответа на сам ping недостаточно: без рабочей
активности обратный pong по-прежнему проверяет связь в обе стороны.

Мёртвые тестировщики продолжают получать ping. Интервал по умолчанию 30 секунд,
ожидание pong — 10 секунд. Назначения переживают перезапуск backend и восстанавливаются
по сроку, а не отправляются повторно без учёта уже выполняющихся задач.
