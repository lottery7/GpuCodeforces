# Формат задачи

Форматы платформы описаны в [docs/backend/formats.md](../../docs/backend/formats.md).
Исходное решение оптимизации (на каждом процессоре задачи) и оба варианта угадывания (на единственном
процессоре задачи) автоматически проходят обычную проверку через судью на тестах задачи. Числа результата
не принимаются из `format.json`. Backend использует результаты этих прогонов; ответ пользователя на угадывание
не запускает еще один прогон. `format.json`, `first.<ext>` и `second.<ext>` не входят в контракт `ProblemSpec`:
backend передает каждый проверяемый исходник как `SubmissionRequest.source` вместе с процессором и языком.

Gateway и executor продолжают возвращать score тестов и итоговый score. Backend может использовать
`benchmark.aggregation`, чтобы вычислить геометрическое среднее score по принятым тестам исходных
решений и пользовательских посылок. Все исходные решения сравниваются на одних тестах и
в одном окружении процессора. Изменение исходников или конфигурации требует новых замеров. Это не меняет
протокол измерения отдельного теста; подробности в документе форматов выше.

Задача — это JSON `ProblemSpec` (см. `judge-api/.../ProblemSpec.kt`), который бэкенд передаёт в каждой посылке, плюс исходник генератора на Python. Списка тестов в JSON нет: тесты объявляет генератор (`tests()`). Пример: `judge/problems/examples/vector_add/` (`problem.json` + `problem.py`; `judge/tools/judge_cli.py` склеивает их в один `ProblemSpec`), для `rtl` — `judge/problems/examples/vector_add_rtl/`, для `riscv-rvv` — `judge/problems/examples/vector_add_riscv/`, для `cuda-sim` — `vector_add_cudasim/`.

## ProblemSpec

```jsonc
{
  "id": "vector-add",                 // [A-Za-z0-9._-]
  "version": "1",                     // для логов; кэш тестов ключуется хэшем содержимого
  "signature": {
    "function": "solve",
    "params": [
      {"name": "A", "type": "FLOAT32", "role": "INPUT",  "memory": "DEVICE", "size": "N"},
      {"name": "C", "type": "FLOAT32", "role": "OUTPUT", "memory": "DEVICE", "size": "N"},
      {"name": "N", "type": "INT32",   "role": "SCALAR"}
    ]
  },
  "generator": {"language": "PYTHON", "source": "<содержимое problem.py>"},
  "checker": {"mode": "TOLERANCE", "rtol": 1e-5, "atol": 1e-6},
  "limits": {"timeLimitMs": 20, "wallTimeLimitMs": null, "memoryLimitMb": 256, "gpuMemoryLimitMb": 256},
  "timing": {"mode": null, "warmupRuns": 1, "maxRuns": 3},
  "compile": {"arch": "sm_86", "flags": ["-std=c++17", "-O3", "--expt-relaxed-constexpr"]},
  "policy": {"allowHeaders": [], "forbidHeaders": [], "forbidSass": [], "allowSass": [], "allowInlineAsm": null},
  "processors": [
    {"id": "gpu-cuda", "languages": ["cuda"]},
    {"id": "rtl", "languages": ["systemverilog"], "limit": 2000000, "rtl": {"readPorts": 1, "dataMode": "MEMORY"}}
  ]
}
```

Процессор и язык посылки задаются рядом с задачей, в `SubmissionRequest.processor` и `SubmissionRequest.language`: процессор выбирается на контест, а не на задачу. Задача только объявляет, где её можно сдавать.

### Процессоры

| Поле | Что это |
|---|---|
| `id` | Процессор из каталога: `gpu-cuda`, `rtl`, `riscv-rvv`, `cuda-sim`, `coral-npu` (см. README). Каждый — не больше одного раза. |
| `languages` | На каких языках процессора можно сдавать задачу: `gpu-cuda` и `cuda-sim` — `cuda`; `rtl` — `systemverilog`; `riscv-rvv` — `c`, `cpp`, `asm`; `coral-npu` — `c`, `cpp`. |
| `limit` | Лимит score одного замерного теста в единицах типа score процессора: мс у `gpu-cuda`, такты у `cuda-sim`, инструкции у `coral-npu`, такты × глубина × транзисторы у `rtl`, условные такты у `riscv-rvv`. Обязателен у всех, кроме `gpu-cuda`; у `gpu-cuda` без него действует `limits.timeLimitMs`. |
| `rtl` | Только у `rtl`: `readPorts` (1..8, портов чтения у каждого читаемого массива) и `dataMode` (`MEMORY` или `STREAM`). |

- `processors` не задан — задача сдаётся только на `gpu-cuda` с языком `cuda` и лимитом `limits.timeLimitMs`. Так работают все пакеты, написанные до процессоров.
- `timing`, `compile`, `policy` и `limits.gpuMemoryLimitMb` относятся к `gpu-cuda`; флаги `compile.flags` действуют и для `cuda-sim`. `limits.memoryLimitMb` и `checker` — общие для всех процессоров.
- `memory` у параметров (`DEVICE`/`HOST`) имеет смысл только для `gpu-cuda` и `cuda-sim`; остальные процессоры его не учитывают.
- Эталонных решений автора в пакете нет. Лимит подбирается так: прогнать своё решение через судью (`judge_cli.py submit … --processor rtl --watch` печатает score) и поставить `limit` с запасом.

### Параметры

| Поле | Значения |
|---|---|
| `type` | `FLOAT16` (`__half`), `BFLOAT16` (`__nv_bfloat16`), `FLOAT32`, `FLOAT64`, `INT8`, `UINT8`, `INT16`, `INT32` (`int`), `UINT32`, `INT64` (`int64_t`), `UINT64`. Скаляры: только 32/64-битные. |
| `role` | `INPUT` → `const T*`; `OUTPUT` → `T*`, проверяется; `INOUT` → `T*`, заполнен входом, проверяется; `SCALAR` → по значению |
| `memory` | `DEVICE` — указатель на память GPU; `HOST` — память CPU. Для массивов обязательно. |
| `size` | число элементов: целочисленное выражение над целыми скалярами (`+ - * / %`, скобки), например `M*K` |

Сигнатура выше превращается в `void solve(const float* A, float* C, int N)` (C++-линковка). Решение с другой сигнатурой получает `COMPILATION_ERROR`.

### Чекер

- `TOLERANCE`: для float `|out − exp| ≤ atol + rtol·|exp|`. NaN совпадает только с NaN, ±Inf — только с тем же Inf. Целые сравниваются точно.
- `EXACT`: побитовое сравнение.

### Время и лимиты

- `timeLimitMs` — лимит на один вызов `solve` на `gpu-cuda` (если у `gpu-cuda` в `processors` не задан свой `limit`), меряется в режиме `timing.mode`. Если режим не задан — `WALL` (весь вызов), где бы ни лежали данные; `GPU_KERNELS` нужно указать явно (см. README).
- `wallTimeLimitMs` — страховочный wall-лимит на вызов.
- `memoryLimitMb` — RAM решения сверх данных теста.
- `gpuMemoryLimitMb` — память GPU сверх буферов теста. `null` — вся GPU.
- `warmupRuns` — прогревы на первом тесте.
- `maxRuns` — максимум прогонов в серой зоне около TL.

### Компиляция и ограничения

- `compile.arch` — архитектура, под которую генерируется код решения (`sm_86`; без PTX и JIT). `null` — архитектура видеокарты профиля. Видеокарта должна уметь исполнять этот код: то же семейство и та же или более ранняя ревизия (`sm_80` на `sm_86` — да; `sm_75` и `sm_89` — нет). Иначе посылка получает `INTERNAL_ERROR` с пояснением.
- `compile.flags` — флаги nvcc для решения, заменяют флаги executor по умолчанию (`null` — оставить их). Разрешены только: `-O0`…`-O3`, `-std=c++11|14|17|20`, `-DИМЯ[=значение]`, `--use_fast_math`, `--fmad=true|false`, `--expt-relaxed-constexpr`, `--expt-extended-lambda`. Любой другой флаг — ошибка валидации (400).
- `policy.forbidSass` / `policy.allowSass` — запрещённые инструкции (опкоды SASS, например `HMMA` для тензорных ядер) поверх политики профиля.
- `policy.allowHeaders` / `policy.forbidHeaders`, `policy.allowInlineAsm` — заголовки и inline asm.

## Процессор `rtl`

Посылка — один файл SystemVerilog с верхним модулем `signature.function` (`solve`); вспомогательные модули — в том же
файле. Пример: `judge/problems/examples/vector_add_rtl/` с решениями на каждый вердикт.

### Интерфейс модуля

Управление: `input clk`, `input start`, `output done`. Скаляр — вход шириной своего типа (`INT32` →
`input logic signed [31:0] N`). Вещественные числа — сырые биты (`FLOAT32` — 32 бита IEEE 754). Адреса — индексы
элементов, 32 бита.

| Массив | `dataMode: MEMORY` (по умолчанию) | `dataMode: STREAM` |
|---|---|---|
| `INPUT A` | `output [31:0] A_addr`, `input [W-1:0] A_data` | `input [W-1:0] A_data`, `input A_valid` |
| `OUTPUT C` | `output [31:0] C_addr`, `output [W-1:0] C_data`, `output C_write` | `output [W-1:0] C_data`, `output C_valid` |
| `INOUT X` | чтение `X_raddr`/`X_rdata`, запись `X_waddr`/`X_wdata`/`X_write` | нельзя (ошибка валидации) |

С `readPorts: k > 1` порты чтения — упакованные массивы: `output logic [k-1:0][31:0] A_addr`,
`input logic [k-1:0][W-1:0] A_data`, порт `i` — `A_addr[i]`/`A_data[i]`. Неупакованные массивы в портах
(`A_addr [k]`) Yosys не читает. Шаблон модуля строит `RtlSignature` (backend показывает его в редакторе, если в пакете
нет `starter.sv`); модуль с другими портами получает `COMPILATION_ERROR` с ожидаемым объявлением порта.

### Такты

- Сброса нет: его роль играет `start`. До первого фронта все регистры — нули, все входы, кроме `start`, уже
  выставлены, `done` должен быть низким (иначе `RUNTIME_ERROR`).
- `start` поднят ровно на первый такт. Такты считаются до фронта `clk`, после которого `done` высокий.
- `MEMORY`: адрес, выставленный на такте `t`, даёт данные на такте `t + 1`; адрес вне массива читает 0. Запись
  происходит на фронте, на котором поднят `*_write`; чтение того же адреса на том же фронте уже видит новое значение.
  Запись за границу массива — `RUNTIME_ERROR` с адресом (текст виден на открытых тестах).
- `STREAM`: с такта после `start` судья подаёт по элементу каждого входного массива за такт по порядку индексов,
  `*_valid` опускается, когда массив кончился (схема не может притормозить поток). Выход судья забирает на каждом
  фронте, где поднят `C_valid`, по порядку индексов; лишний элемент — `RUNTIME_ERROR`.
- Выходные массивы перед тестом заполнены байтами `0xFF`, как на `gpu-cuda`.

### Score и лимит

- Score замерного теста = такты × глубина × транзисторы. Все три числа считает Yosys по нетлисту после
  `synth -top solve -flatten` и `dffunmap` (триггеры с enable и синхронным сбросом становятся обычными триггерами с
  мультиплексором перед ними — поведение то же):
  - **транзисторы** — площадь схемы: оценка `stat -tech cmos`, у каждого типа ячейки свой вес (инвертор — 2, И-НЕ — 4,
    исключающее ИЛИ — 12, мультиплексор — 12, триггер — 16);
  - **глубина** — число ячеек на самом длинном пути между триггерами и портами (`ltp -noff`): она задаёт, на какой
    частоте схема могла бы работать, поэтому длинная комбинационная логика не бесплатна. Схема из одних проводов
    считается глубиной 1;
  - **такты** — до `done`, их считает тестбенч.

  Память судьи в площадь не входит; память внутри схемы после синтеза разложена на триггеры и входит. В `metrics`
  результата — `cycles`, `depth`, `transistors` и `cells` (число ячеек, для сведения).
- Схема должна быть синхронной: защёлки и триггеры с асинхронным сбросом или установкой Yosys взвесить не умеет, такая
  посылка — `COMPILATION_ERROR` с перечнем ячеек. Сбрасывайте регистры по `start`. Комбинационная петля —
  тоже `COMPILATION_ERROR`: у неё нет самого длинного пути.
- Тест останавливается через `floor(limit / (глубина × транзисторы))` тактов без `done` — `TIME_LIMIT_EXCEEDED`
  («Cycles x depth x transistors limit exceeded»). Незамерный тест ограничен потолком судьи
  (`judge.executor.rtl.max-cycles`, 10⁸ тактов), он же ограничивает и замерные. Плюс 60 секунд реального времени на тест.
- Симулируется нетлист после синтеза (Verilator, `--x-initial 0`), то есть ровно та схема, чью площадь посчитали.
  `$display` синтез выбрасывает, `$finish`, `$fopen`, `$system` — ошибка синтеза, `COMPILATION_ERROR`.
- `` `include `` и `$readmemh`/`$readmemb` запрещены проверкой исходника (`POLICY_VIOLATION`): они читали бы файлы
  машины при синтезе. Граница безопасности при этом — песочница nsjail, в которой нет ни тестов, ни ответов.
- Схема больше 10⁶ ячеек — `COMPILATION_ERROR`. Модуль, который не определён в посылке (чёрный ящик), — тоже.

## Процессор `riscv-rvv`

Посылка — функция `solve` на C (`.c`, `-std=gnu17`), C++ (`.cpp`, `-std=gnu++17`) или ассемблере RISC-V (`.S`):
`void solve(const int32_t* A, const int32_t* B, int32_t* C, int32_t N)`. Все массивы — в обычной памяти (поле
`memory` не учитывается), выровнены на 64 байта, выходы перед вызовом заполнены байтами `0xFF`. У C++ обычная
C++-линковка: обвязку судья компилирует тем же компилятором. Пример: `judge/problems/examples/vector_add_riscv/`.

- Процессор один на все задачи: RV64GCV, VLEN = 256 бит, флаги судьи `-O2 -march=rv64gcv -mabi=lp64d -static`
  (GCC 13.3), QEMU 11.1.3 в user mode. Флаги задача не меняет.
- Score замерного теста = инструкции + 10 × промахи L1 + 100 × промахи L2 (оценка тактов в духе Cachegrind) за
  вычетом того же для обвязки судьи с пустой `solve` на том же тесте. Кэши моделирует плагин судьи: L1I и L1D по
  32 КиБ, 8 путей; общий L2 1 МиБ, 16 путей; строка 64 байта, LRU. Векторная инструкция — одна инструкция, её
  обращения к памяти идут через кэш по элементам. В `metrics` — `instructions`, `l1_misses`, `ll_misses` (и
  `denied_syscalls`, если решение пробовало запрещённые вызовы).
- Лимит: тест останавливается, когда решение выполнило `limit` инструкций сверх обвязки (score не меньше числа
  инструкций), — `TIME_LIMIT_EXCEEDED` («Instruction limit exceeded»). Незамерный тест ограничен потолком судьи
  (`judge.executor.riscv.max-instructions`, 5·10⁹), он же ограничивает и замерные. Плюс 120 секунд реального времени.
- Решение однопоточное и не выходит за свои данные: `fork`, потоки, `exec`, открытие файлов вне каталогов теста и
  любые операции с каналом отчёта судьи (stdout) отклоняются (`EPERM`) и считаются. stderr свободен для отладки.
- Падение (например, SIGSEGV) и ненулевой код выхода — `RUNTIME_ERROR`. Ошибка компиляции — `COMPILATION_ERROR`
  с сообщениями компилятора.

## Процессор `coral-npu`

Посылка — функция `solve` на C (`.c`, `-std=gnu17`) или C++ (`.cpp`, `-std=gnu++17`):
`void solve(const int32_t* A, const int32_t* B, int32_t* C, int32_t N)`. Она исполняется на ядре Coral NPU без
операционной системы: ни файлов, ни вывода, ни системных вызовов. Пример:
`judge/problems/examples/vector_add_coral/`.

- Процессор один на все задачи: ядро RvvCoreMini в Renode 1.17.0 — RV32IMF с Zbb и векторным расширением Zve32x/
  Zve32f, VLEN = 128 бит, сжатых инструкций нет. Флаги судьи: `-O2 -march=rv32imf_zve32f_zicsr_zifencei_zbb
  -mabi=ilp32f -fno-math-errno` (GCC 13.2), библиотека C — picolibc. Флаги задача не меняет.
- Память — это память ядра: **8 КБ кода** (только исполнение, прочитать её как данные нельзя) и **32 КБ данных**. В
  данных лежат константы, глобальные переменные и стек решения и **все массивы теста**, выровненные на 16 байт; выходы
  перед запуском заполнены байтами `0xFF`. Стек растёт вниз от конца памяти данных, ему гарантирован 1 КБ. Тесты для
  этого процессора должны быть маленькими: `"processors": ["coral-npu"]` у теста (см. «Какой тест где идёт»).
  `limits.memoryLimitMb` на этом процессоре не действует.
- Score замерного теста — число инструкций, которые ядро выполнило до остановки, считая около двадцати инструкций
  стартового кода судьи. Векторная инструкция — одна инструкция, сколько бы элементов она ни обработала.
- Лимит: тест останавливается вскоре после `limit` инструкций — `TIME_LIMIT_EXCEEDED` («Instruction limit
  exceeded»). Незамерный тест ограничен потолком судьи (`judge.executor.coral-npu.max-instructions`, 2·10⁹), он же
  ограничивает и замерные. Плюс 60 секунд реального времени.
- Код не поместился в 8 КБ — ошибка компоновщика (`region ITCM overflowed`), то есть `COMPILATION_ERROR`. Данные
  решения вместе с массивами теста и запасом стека не поместились в 32 КБ — `MEMORY_LIMIT_EXCEEDED` на этом тесте.
- Обращение мимо двух памятей ядра (ядро поднимает FAULT) и любое исключение (недопустимая инструкция, `ecall`,
  `ebreak`) — `RUNTIME_ERROR`. Переполнение стека не отслеживается: стек молча затрёт массивы теста.
- C++ — без стандартной библиотеки (её для этой цели нет), исключений и RTTI: заголовки C (`<stdint.h>`,
  `<string.h>`, `<math.h>`) и `<riscv_vector.h>` доступны. Конструкторы глобальных объектов выполняются до `solve`
  и входят в score.
- В C++ параметры `solve` объявляются теми же типами, что в шаблоне решения (`int32_t`, а не `int`): на этой цели
  `int32_t` — это `long`, и `solve(..., int)` — другая функция, которую компоновщик не найдёт
  (`COMPILATION_ERROR`). В C это не играет роли.

## Процессор `cuda-sim`

Посылка — CUDA, как на `gpu-cuda` (та же сигнатура `solve`), но исполняется в GPGPU-Sim (форк accel-sim, коммит
`4195dd4f`) на модели QV100: PTX `compute_70` в бинарнике, `libcudart` симулятора. Пример:
`judge/problems/examples/vector_add_cudasim/`.

- Все массивы задачи — `DEVICE` (иначе ошибка валидации): работа на CPU в симуляторе не стоит тактов. По той же
  причине `cudaMemcpy*` в решении запрещены (`POLICY_VIOLATION`; проверка символов, рекомендательная).
- Score замерного теста — `gpu_tot_sim_cycle` за вызов `solve` (все ядра), в `metrics` — `cycles` и `instructions`.
  Лимит тактов — параметр симулятора `-gpgpu_max_cycle` (`limit`, но не больше 10⁷); превышение —
  `TIME_LIMIT_EXCEEDED`. Незамерные тесты идут в функциональном режиме (`-gpgpu_ptx_sim_mode 1`), без тактов.
- Не поддержаны: CUDA Graphs и текстурные объекты (их нет в `libcudart` симулятора — `COMPILATION_ERROR` с этим
  объяснением), warp-shuffle `__shfl_*_sync` (GPGPU-Sim считает их неверно — `POLICY_VIOLATION`). Библиотеки поверх
  CUDA (cuBLAS и т. п.) — вне скоупа.
- Симулятор живёт в процессе решения и печатает статистику в общий stdout: решение могло бы напечатать поддельные
  строки (ограничение принято, см. README судьи).

## Генератор (problem.py)

Для пользовательских тестов задайте `allowCustomTests: true` и добавьте
`validate_input(test, inputs)`, возвращающую `True` только для входа, допустимого
по условию задачи. При `False` тест отклоняется; исключение означает ошибку задачи.
Входы передаются как данные в `ProblemSpec.customTests` (`scalars` и `inputs`),
эталонные ответы вычисляет обычная `reference()`. При `customOnly: true` запускается
только один кандидат взлома; иначе дополнительные тесты идут после основных.
Дополнительные тесты идут на любом процессоре задачи как тесты с `"measure": False`:
проверяется только ответ, в score посылки они не входят.
Их содержимое и режим входят в ключ кэша. Ограничения и API описаны в
[правилах участия](../../docs/backend/participation.md).

Выполняется один раз на версию задачи на GPU-машине (Python 3.12, PyTorch 2.9.1). Задачи приходят через PR в общий репозиторий, поэтому генератор запускается в той же песочнице, что и решения: сети нет, писать можно только в свою рабочую папку и `/tmp`.

Модуль определяет три функции:

```python
import torch

def tests():
    """Тесты задачи по порядку (список или генератор dict). Проверка останавливается на первом упавшем."""
    # пример из условия: входы и ответ записаны руками
    yield {"name": "sample", "sample": True, "scalars": {"N": 4},
           "inputs": {"A": [1, 2, 3, 4]}, "expected": {"C": [2, 4, 6, 8]}}
    for i, n in enumerate([1, 1000003, 100_000_000]):
        yield {"name": f"random-{n}", "scalars": {"N": n}, "seed": i}

def generate(test, gen, device):
    """Входы теста без рукописных inputs.
    test.index, test.name, test.seed, test.sample, test.scalars (dict), test.sizes (dict: param -> число элементов);
    test["N"] — короткая запись для test.scalars["N"].
    gen — torch.Generator на `device`, засеянный test.seed. Используйте его для детерминизма.
    Вернуть dict: имя -> тензор для КАЖДОГО INPUT/INOUT, dtype как в сигнатуре, test.sizes[name] элементов (форма любая)."""
    n = test["N"]
    return {"A": torch.empty(n, device=device).uniform_(-1, 1, generator=gen)}

def reference(test, inputs):
    """Эталон. inputs — копии входов (менять можно). Вернуть dict для КАЖДОГО OUTPUT/INOUT."""
    return {"C": inputs["A"] * 2}
```

### Тест из `tests()`

| Ключ | Обяз. | Что это |
|---|---|---|
| `name` | да | Уникальное имя, до 128 символов. |
| `scalars` | да | Значения всех скаляров сигнатуры, ровно их. Из них вычисляются размеры массивов. Целые скаляры должны помещаться в свой тип. |
| `sample` | нет | `True` — тест открытый: участник увидит детали расхождения и свой stderr. По умолчанию `False`. |
| `seed` | нет | Зерно для `gen` в `generate()`. По умолчанию — номер теста (с 1). |
| `inputs` | нет | Входы, записанные руками (все `INPUT`/`INOUT`): списки чисел или тензоры. Для такого теста `generate()` не вызывается. |
| `expected` | нет | Ответы, записанные руками (все `OUTPUT`/`INOUT`), только вместе с `inputs`: пример из условия проверяется по тому, что написано в условии, а не по тому, что посчитал эталон. Без `expected` ответ считает `reference()`. |
| `processors` | нет | Список id процессоров задачи, на которых идёт тест. Нет поля — тест идёт на всех процессорах задачи. |
| `measure` | нет | `False` — с теста не снимается score: проверяется только ответ, лимит score к нему не применяется. По умолчанию `True`. |

- Тестов от 1 до 200, данные одного теста — не больше 4 ГБ.
- `tests()` должна давать один и тот же список при каждом запуске: тесты генерирует каждый executor сам. Глобальные `random` и `torch` засеваются нулём перед вызовом, но лучше не использовать случайность в самом списке, а оставить её `generate()` через `seed`.
- `generate()` можно не определять, если у всех тестов есть `inputs`.
- Тесты идут на процессоре в порядке объявления; на каждом процессоре тесты нумеруются заново, с 1. `seed` по умолчанию — номер теста среди всех объявленных, так что один и тот же тест получает одни и те же данные на всех процессорах.

### Какой тест где идёт

Большой тест для реальной GPU эмулятору не под силу, поэтому тесту можно указать процессоры, а маленькому проверочному тесту — не снимать с него score:

```python
def tests():
    yield {"name": "big",    "scalars": {"N": 100_000_000}, "processors": ["gpu-cuda"]}
    yield {"name": "small",  "scalars": {"N": 1024},        "processors": ["rtl", "riscv-rvv", "cuda-sim", "coral-npu"]}
    yield {"name": "single", "scalars": {"N": 1},           "measure": False}
```

Для задачи с процессорами `gpu-cuda`, `rtl`, `riscv-rvv`, `cuda-sim`, `coral-npu`:

| Тест | `gpu-cuda` | `rtl` | `riscv-rvv` | `cuda-sim` | `coral-npu` |
|---|---|---|---|---|---|
| `big` | замерный | — | — | — | — |
| `small` | — | замерный | замерный | замерный | замерный |
| `single` | только ответ | только ответ | только ответ | только ответ | только ответ |

- Score посылки — максимум score по замерным тестам её процессора; тест, превысивший лимит, — `TIME_LIMIT_EXCEEDED` с названием единицы.
- **У каждого процессора задачи должен быть хотя бы один замерный тест.** Иначе ошибка: `processor rtl has no measured test: add a test with "processors": ["rtl"] (or without "processors") that does not set "measure": False`.
- Процессор, которого задача не объявляет: `test 1 'big': unknown processor "gpu"; the problem declares gpu-cuda, rtl`.
- `judge_cli.py validate` печатает по каждому процессору число тестов и число замерных (`rtl: 2 tests, 1 measured`), если генератор импортируется локально (нужен torch).
- Эталонный ответ не может состоять из одних байтов `0xFF` (NaN для float, −1 или максимум для целых): этим шаблоном обвязка заполняет выходы перед каждым вызовом, и решение, которое ничего не пишет, прошло бы такой тест. Задача с таким тестом отклоняется.
- Gateway проверяет только JSON задачи. Ошибки в `tests()` (неизвестный ключ, не те скаляры, слишком большой тест) видны только при генерации тестов: первая посылка получает `INTERNAL_ERROR` («Tests of this problem could not be generated»), подробности — в логе executor. Проверяйте задачу локально (ниже) или в CI репозитория задач.
- Эталон считается в строгом IEEE fp32: TF32 выключен, детерминированные алгоритмы. Для точности можно считать в fp64 и вернуть в нужном типе (см. `matmul_host`).
- Неверные ключи, dtype или размеры — понятная ошибка. Посылка получает `INTERNAL_ERROR` («Tests of this problem could not be generated»), в логе executor есть traceback.
- Локальная проверка генератора (нужен torch):

```bash
PYTHONPATH=judge/pytools python3 -m judge_problem.prepare --spec problem.json --source problem.py --out /tmp/out --processor rtl
```

  Как `spec.json` годится сам `problem.json` задачи (нужны `signature` и `processors`). Без `--processor` генерируются все тесты. В `/tmp/out/tests.json` будет список тестов, который увидит судья на этом процессоре.
